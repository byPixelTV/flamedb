# FlameDB Next Task: Production-Grade Ingestion & Replication

## Goal

Move FlameDB from “fast prototype” toward production-grade ingestion for large Minecraft networks. Focus on:

1. Native batched writes.
2. SDK-friendly pipelining.
3. Reliable async replication with crash recovery.
4. Better overload/backpressure behavior.

Target context: FlameDB should eventually support DonutSMP/Hypixel-like workloads: tens of thousands concurrent players, millions of writes/day, eventually billions of events.

## Current State

Relevant existing code:

- `cmd/benchmark/main.go`
  - Supports `--metrics`, `--addrs`, `--route topology`, and `--pipeline`.
  - Can fetch `CLUSTER_TOPOLOGY`.
- `internal/server/server.go`
  - TCP server, auth, query parsing, routing, replication trigger.
  - Has `CLUSTER_TOPOLOGY`.
  - Has internal `REPL_BATCH`.
- `internal/cluster/replication.go`
  - Async replication via fanout queues and per-node batch queues.
  - No intentional dropping now; uses backpressure and retry.
  - Still in-memory only, so pending replication is lost on process crash.
- `internal/storage/storage.go`
  - Pebble-backed writes through `WriteBatcher`.
  - Latest-event cache for `GET metric LIMIT 1 ORDER DESC`.
- `internal/query/parser.go`
  - Supports `WRITE`, `GET`, `SET`, `DELETE`, etc.
  - Internal flags `__replica` and `__local`.
- `internal/query/executor.go`
  - Executes parsed queries.
- Configs currently use `replication_factor: 2` for 4-node cluster tests.

## Important Principle

Do not optimize by weakening correctness silently.

Async replication may be eventually consistent, but it must not silently lose acknowledged writes. If durability is not guaranteed for a mode, name that mode explicitly and document it.

## Task 1: Add Native WRITE_BATCH Command

Add a protocol command for batched ingestion.

Suggested syntax:

```txt
WRITE_BATCH
WRITE metric1 1 tag="x"
WRITE metric2 5 lb="player"
WRITE metric3 10 ts=123
END
```

Alternative acceptable syntax if simpler:

```txt
WRITE_BATCH [{"metric":"kills","value":1,"tags":{"player":"pixel"}}, ...]
```

Prefer newline batch because the current protocol is newline-oriented and avoids large JSON overhead.

Requirements:

- One auth session can send batch commands over the existing TCP connection.
- Batch returns one response line.
- Response should include:
  - `ok`
  - accepted count
  - failed count
  - optional per-item errors only when failures exist
- Batched writes should route efficiently:
  - If batch arrives at a node and contains multiple metrics, group by owner/locality.
  - Local eligible writes execute locally.
  - Non-local writes forward in batches to correct owner/replica where possible.
- Preserve existing single `WRITE` behavior.
- Support `QUORUM` either:
  - per item, if present in the line, or
  - at batch level if command supports it.
- `__replica` must prevent replication loops.

## Task 2: Storage Batch API

Current `Storage.WriteEvent` calls `batcher.Add` per event. Add a proper multi-event API.

Suggested API:

```go
func (s *Storage) WriteEvents(events []Event, sync bool) error
```

Requirements:

- Build one Pebble batch for all event keys and secondary indexes.
- Update cardinality async.
- Update latest cache for each metric.
- Avoid per-event locking where possible.
- Preserve `WriteEvent` by delegating to `WriteEvents`.

Watch out:

- Tags create secondary indexes.
- Timestamp defaulting probably belongs in query/executor layer, not storage.
- Keep memory use bounded for huge batches.

## Task 3: Executor Batch API

Add executor support for batch writes.

Suggested API:

```go
func (e *Executor) ExecuteBatch(queries []*query.Query) (*BatchResult, error)
```

Requirements:

- Group plain event writes and call `Storage.WriteEvents`.
- Leaderboard updates still need care because they use per-entity locks and read-modify-write.
- If a batch mixes leaderboard writes and plain writes, handle both correctly.
- Do not let one bad item corrupt unrelated good items unless batch is explicitly atomic.
- Decide and document semantics:
  - Best default: partial success with per-item error reporting.
  - Optional future mode: atomic batch.

## Task 4: Persistent Replication Outbox

Current async replication queues are in memory only. Add a durable outbox.

Goal: once a primary/local owner acknowledges a write, pending replica delivery should survive process restart.

Suggested design:

- Store pending replication records in Pebble using reserved keys:
  - `repl-outbox:<targetNodeID>:<seq>` -> encoded batch or command
- On async replication enqueue:
  - persist outbox record locally first
  - enqueue in memory
- When target confirms replication:
  - delete outbox record
- On startup:
  - scan `repl-outbox:` keys
  - resume delivery
- Use monotonic local sequence IDs.
- Batch outbox writes/deletes for efficiency.

Requirements:

- No silent loss if process crashes after client ack.
- Retry with backoff remains.
- If target node is gone, keep retrying or expose lag/unhealthy state.
- Add internal metrics/logs for outbox depth and replication lag.

This is the most important correctness piece.

## Task 5: Improve REPL_BATCH

Current `REPL_BATCH` sends joined query strings with separator.

Improve it if needed for durability and speed.

Options:

- Keep textual frame for now.
- Or add binary/JSON encoded batch payload.
- Avoid large reflection-heavy JSON if performance suffers.
- Must handle scanner buffer limits safely.
- Must not allow client-level users to fake unsafe internal commands unless authenticated and authorized.

Potential design:

```txt
REPL_BATCH <base64 or compact payload>
```

or

```txt
REPL_BATCH
WRITE ...
WRITE ...
END
```

## Task 6: Backpressure & Overload Behavior

Current queues now block instead of dropping.

Add explicit overload behavior:

- Configurable max queue sizes.
- If local ingestion cannot enqueue replication outbox fast enough, return a clear error:
  - `{"error":"server busy"}`
- Expose queue depth internally.
- Avoid unbounded memory growth.
- Avoid goroutine explosions.

## Task 7: Benchmark Updates

Extend benchmark to test realistic ingestion modes:

- `--batch-size N`
- `--pipeline N`
- `--route topology`
- `--mode write`
- `--mode mixed`
- `--metrics N`

Recommended test matrix:

```powershell
# Single request baseline
go run ./cmd/benchmark --addr ... --workers 200 --duration 15s --metric bench --metrics 64 --mode mixed --route topology

# Pipelined
go run ./cmd/benchmark --addr ... --workers 200 --duration 15s --metric bench --metrics 64 --mode write --route topology --pipeline 64

# Native batch
go run ./cmd/benchmark --addr ... --workers 200 --duration 15s --metric bench --metrics 64 --mode write --route topology --batch-size 100
```

Report:
- writes/sec
- reads/sec
- errors
- p50/p99
- maybe batch latency separately

## Task 8: Tests

Add unit/integration tests for:

- Parsing `WRITE_BATCH`.
- Executing batch writes.
- Mixed good/bad batch behavior.
- Replica batch does not re-replicate.
- Outbox record is created before async ack.
- Outbox record is deleted after successful replica ack.
- Outbox recovery on startup.
- Topology command returns RF/VNodes/nodes.
- No data loss under simulated replica connection failure.

If full integration is hard, add narrow tests around outbox encode/decode and replay first.

## Non-Goals For This Task

Do not build the Java/Kotlin SDK yet.

Do not build a dashboard.

Do not implement TTL/backup unless required for outbox cleanup.

Do not redesign the whole query language.

Do not remove existing single-line commands.

## Success Criteria

This task is successful when:

- Single writes still work.
- Batch writes work.
- Benchmark can use native batch mode.
- Async replication no longer depends only on in-memory queues.
- Restarting a node with pending replication does not lose acknowledged writes.
- Cluster can run RF=2 with owner/topology routing without replication drops.
- Code remains simple enough for SDK work to build on.

## Suggested Implementation Order

1. Add `Storage.WriteEvents`.
2. Add executor batch support.
3. Add `WRITE_BATCH` parser/server handling.
4. Add benchmark `--batch-size`.
5. Add durable outbox.
6. Wire async replication through outbox.
7. Add recovery replay on startup.
8. Add tests and run benchmarks.
