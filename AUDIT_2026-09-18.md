# FlameDB Audit - September 18, 2026

## Changes

The review covered the server, parser/executor, Pebble storage, leaderboards, cluster communication, replication, rebalancing, and the Go, TypeScript, and Kotlin SDKs. At the time of the audit, the changes were local; no release had been published and no existing user database had been migrated.

### Security and protocol

- Internal cluster commands, `REPL_BATCH`, `__replica`, `__local`, and operation IDs now require internal authorization. Regular write keys no longer grant access to cluster administration or data exports.
- Added a separate `auth.internal_key`, alternatively supplied through `FLAMEDB_INTERNAL_KEY`. The environment value is not written to disk when saving configuration. Cluster configurations without an internal key are rejected at startup.
- Empty, duplicate, and multiline keys are rejected. The example configuration binds only to loopback; its `test` key is exclusively for local development.
- Limits: 1,024 active connections, a 10-second authentication deadline, 30 seconds to receive a batch, 10,000 batch entries, and an 8 MiB payload. Incomplete batches are not executed. Replication frames are also split.
- Fixed parser crashes on incomplete `SET`/`DELETE` arguments and infinite loops/overflows in time expressions. Negative pagination, nonfinite values, and reserved metric names are rejected. Quoted strings support escapes.
- Each request produces exactly one response, including replica-batch and multi-metric errors. Malformed JSON responses are not treated as successful empty responses.

### Storage and replication

- Events and leaderboard changes are written atomically together. Absolute `SET` values and `DELETE` use synchronized entity mutations; negative scores and zero values are sorted correctly.
- `DELETE <metric> [FROM ...] [TO ...]` now deletes raw data and its tag indexes. Unsupported tag filters are rejected to prevent unintentionally broader deletions.
- Removed the faulty latest-value cache: it could return unwritten/stale data, mistake historical writes for the latest values after restarts, and violate the exclusive TO boundary.
- Automatically assigned timestamps are unique within a running executor and are replicated unchanged. Relative DELETE time boundaries are resolved to absolute values for replication.
- New replication operations carry persistent IDs. The replica receipt, event, and optional score are stored atomically. Retrying after a lost response or restart therefore does not increment a score again.
- Local server writes and new outbox entries are synced before a successful response. Quorum counts only actual successful responses and follows the configured replication factor. Failed deliveries remain stored for retry.
- Quorum and async writes use the same delivery path; a quorum write cannot overtake earlier async operations. The primary preserves local mutation and replication ordering. Client writes are therefore routed to the primary.
- Removed unsafe automatic write retries from connection pooling/forwarding. Outcomes can still be unknown after transport failures; applications must not blindly retry increments.
- Recovery runs in the background; new deliveries wait for the old outbox to be enqueued. Shutdown closes server connections and background workers before Pebble.
- Rebalance imports rebuild tag indexes; batch and iterator resources are closed.

### Performance

- Fixed time windows jump directly to the event timestamp instead of iterating through every window since 1970. Local microbenchmark: approximately **88 ns/op**, 24 B/op for a modern event with `GROUP BY 1s`. This is not an overall throughput benchmark.
- ASC and DESC pagination bound storage scans. Tag queries read indexes and events from the same snapshot and also validate the selected index tag.
- Index selection favors higher distinct counts as a selectivity heuristic. Skewed value distributions remain a limitation of this heuristic.
- Bounded lock stripes and 16 fanout shards replace unbounded entity locks and per-metric queues. Replica WRITE batches sync plain events together.
- Cardinality and leaderboard caches no longer leak cleanup goroutines; the executor no longer uses the potentially stale leaderboard result cache.

### SDKs

- Go: correct score/group/stats fields, IPv6 addresses, context cancellation and deadlines, errors instead of panics after Close, connection cleanup after authentication failures/ambiguous transport errors, safe string encoding, and identifier validation.
- TypeScript: a single shared authentication handshake, no lost early greetings, correct UTF-8 handling across TCP chunks, a bounded pipeline, connection-wide termination on ambiguous timeouts, correct result fields, and safe string encoding.
- TypeScript adds exact `bigint` companion fields `Event.timestampNs` and `SeriesPoint.tsNs`; existing numeric fields remain compatible. `WriteOptions.timestampNs` accepts `bigint`. Node.js >= 22 is required. Convert BigInt values appropriately before calling `JSON.stringify` on containing objects.
- Kotlin: connection timeout, explicit UTF-8, socket cleanup on authentication/transport errors, validated and buffered writes, correct stats envelope, and safe identifier/string handling.

## Upgrading existing installations

1. Drain the old replication outbox and stop all nodes. Old outbox records without operation IDs do not benefit from the new deduplication. Upgrade servers together; mixed-version rolling upgrades have not been tested.
2. The new binary automatically detects legacy Pebble databases when opening them. Under an exclusive database lock, it first creates a checkpoint at `<data_path>.pre-v2-<random ID>/db`, verifies that it can be opened, and only then upgrades the format at the existing data path. A backup failure aborts startup before the format upgrade. Databases already using a supported format are not migrated again. Pebble persists individual format transitions so an interrupted upgrade can resume on the next startup.
3. `server.data_path` remains unchanged. The startup log contains the exact backup path. Backups are not automatically deleted. To roll back, stop the server and point the old binary at a separate copy of the checkpoint; this copy will not contain writes made after migration. A checkpoint may share immutable SST files through hard links and does not replace an independent external backup. Allow enough free space for the checkpoint, WAL, and potential compactions. Do not open the active v2 directory with the old binary. Alternatively, manual copying to a new directory remains available:

   ```powershell
   go run ./cmd/migrate -source ./data-node1 -destination ./data-node1-v2
   ```

   Update `server.data_path` to the destination only when using this manual alternative. The copy tool opens the source directory read-only.
4. Supply the same random cluster secret to all nodes through `FLAMEDB_INTERNAL_KEY` or `auth.internal_key`. Keep client API keys separate. Configure network binding deliberately; the example configuration now binds to `127.0.0.1`.
5. Start the nodes and check topology, the outbox, and application-specific queries.

## Validation

- `go test -race ./...` and `go vet ./...` for the server, including the copy tool.
- Separate Go SDK tests, including the race detector and vet.
- TypeScript build and TCP integration tests: concurrent handshake, pipeline timeout, Unicode, result formats, injection boundaries, and exact nanoseconds.
- Kotlin build and TCP tests with the updated Gradle wrapper.
- Two real local TCP nodes: forwarded quorum batch, identical timestamps/leaderboards, and async SET ordered before quorum WRITE.
- Automatic migration covering old SST files, preserved checkpoints, restarts, locked databases, and failed/incomplete backups.
- Outbox restart, delivery, and removal after ACK; replica deduplication across restarts; rejection of unauthorized internal commands; migration with an unchanged source.
- Parser fuzzing: **505,111 executions in approximately 21 seconds**, no failures.
- `govulncheck`: no known Go vulnerabilities in the checked version. `npm audit`: no reported vulnerabilities. No separate Maven vulnerability scanner was run.

## Remaining operational limitations

- TCP remains unencrypted. Transport protection is required outside a trusted network; native TLS support is not implemented.
- This is not a consensus database. Network partitions, concurrent ring membership changes, and live rebalancing with concurrent writes have not been covered by full chaos or long-running tests. Rebalancing still does not provide continuous anti-entropy reconciliation for existing metrics.
- Persistent deduplication receipts are intentionally not removed automatically: without a guaranteed end to the retry window, removal would allow duplicate increments. Their storage requirements therefore grow with the number of replicated operations.
- Aggregations over very large time ranges still materialize events. Bounded GET queries now scan efficiently; aggregating billions of events requires further streaming work.
- An error after a local commit, a quorum timeout, or a disconnected connection can affect a write that has already been applied. Internal deduplication is not a public idempotency-key API for arbitrary client retries.
- No production rollout, complete network-partition test, or proof of the 100k ops/s target was performed. Synchronous durability may increase single-write latency; native batches amortize this cost.
